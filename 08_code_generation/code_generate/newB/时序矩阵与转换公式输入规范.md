# 时序矩阵与转换公式输入规范

本文档用于细化协议转换项目生成器的两类核心输入：

- `choreography.json`：联合转换场景下的时序矩阵输入
- `mappings.json`：转换公式输入

设计目标：

1. **单链路简单转换**时，不强制提供时序矩阵
2. **联合转换**时，时序矩阵可完整描述多源消息的触发关系
3. 转换公式 JSON 能稳定生成 `xxx_to_yyy.cpp`
4. 输入格式足够严格，便于后续做自动校验和代码生成

---

## 1. 文件职责

### 1.1 `choreography.json`

用于描述：

- 哪些源消息参与联合转换
- 哪些目标链路需要编排
- 每条目标链路的缓存有效时间
- 各源消息之间的时序关系矩阵
- 目标消息输出策略

它最终生成：

- `to_code_Choreography.h`
- `to_code_Choreography.cpp`
- `messageconvert.cpp` 中的联合触发逻辑

### 1.2 `mappings.json`

用于描述：

- 转换链有哪些
- 每条转换链的源协议、目标协议
- 每个目标字段如何从源字段计算出来
- 哪些字段是常量、直接映射、表达式映射、条件映射

它最终生成：

- `xxx_to_yyy.h`
- `xxx_to_yyy.cpp`

---

## 2. 使用原则

### 2.1 simple 模式

如果项目是**单源单目标**转换，则：

- 必须提供协议 XML
- 必须提供 `mappings.json`
- **不需要** `choreography.json`

生成结果类似：

- `newC`
- `newD`

### 2.2 joint 模式

如果项目是**联合转换/多链路编排**，则：

- 必须提供协议 XML
- 必须提供 `mappings.json`
- 必须提供 `choreography.json`

生成结果类似：

- `newB`

---

## 3. `choreography.json` 规范

## 3.1 设计目标

该文件不直接描述字段映射，只描述：

- 哪些消息参与编排
- 编排采用什么时序约束
- 目标消息的缓存/输出策略

也就是说，它是**流程级输入**，不是字段级输入。

---

## 3.2 顶层结构

推荐格式：

```json
{
  "version": "1.0",
  "mode": "joint",
  "project_name": "peach",
  "sources": [],
  "targets": [],
  "joint_groups": []
}
```

字段说明：

- `version`
  - 规范版本号
  - 必填
  - 当前建议固定为 `"1.0"`

- `mode`
  - 项目模式
  - 必填
  - 联合转换时必须为 `"joint"`

- `project_name`
  - 工程名
  - 必填

- `sources`
  - 参与编排的源消息列表
  - 必填

- `targets`
  - 受编排控制的目标消息列表
  - 必填

- `joint_groups`
  - 联合触发组
  - 必填

---

## 3.3 `sources` 结构

推荐格式：

```json
{
  "id": "S01",
  "protocol": "S协议.S0_1",
  "message_type": "S0_1",
  "cache_key": "S01",
  "required": true
}
```

字段说明：

- `id`
  - 源消息短标识
  - 必填
  - 需在本文件内唯一
  - 用于矩阵行列名

- `protocol`
  - 源消息展示名
  - 必填
  - 用于生成编排文件中的字符串常量

- `message_type`
  - 源协议对象类型
  - 必填
  - 例如 `S0_1`、`S106`

- `cache_key`
  - 运行时缓存中使用的名字
  - 必填
  - 例如 `S01`

- `required`
  - 是否必须参与联合触发
  - 可选
  - 默认 `true`

---

## 3.4 `targets` 结构

推荐格式：

```json
{
  "id": "W304",
  "protocol": "W协议.W30_4",
  "message_type": "W304",
  "template_name": "S01ToW304",
  "receive_window_ms": 200,
  "initial_status": "direct"
}
```

字段说明：

- `id`
  - 目标消息短标识
  - 必填
  - 需唯一

- `protocol`
  - 目标协议展示名
  - 必填

- `message_type`
  - 目标协议对象类型
  - 必填

- `template_name`
  - 对应转换模板名
  - 必填
  - 用于生成 `to_code_Choreography.cpp` 中的模板列表

- `receive_window_ms`
  - 目标消息缓存有效时间
  - 必填
  - 单位毫秒
  - 大于等于 `0`

- `initial_status`
  - 初始输出状态
  - 可选
  - 允许值：
    - `direct`：直接输出
    - `cache`：先缓存等待
  - 默认 `direct`

---

## 3.5 `joint_groups` 结构

这是核心部分。

推荐格式：

```json
{
  "group_id": "joint_1",
  "target_id": "W304",
  "sources": ["S01", "S106"],
  "trigger_policy": "all_required",
  "matrix": {
    "unit": "ms",
    "rows": ["S01", "S106"],
    "cols": ["S01", "S106"],
    "values": [
      [0, 200],
      [200, 0]
    ]
  }
}
```

字段说明：

- `group_id`
  - 联合触发组 ID
  - 必填
  - 唯一

- `target_id`
  - 该联合组对应的目标消息
  - 必填
  - 必须存在于 `targets.id`

- `sources`
  - 参与该联合组的源消息列表
  - 必填
  - 每个值必须存在于 `sources.id`

- `trigger_policy`
  - 触发策略
  - 必填
  - 允许值：
    - `all_required`
    - `any_required`
    - `min_count`

- `matrix`
  - 时序矩阵
  - 必填

---

## 3.6 `matrix` 结构定义

推荐格式：

```json
{
  "unit": "ms",
  "rows": ["S01", "S106"],
  "cols": ["S01", "S106"],
  "values": [
    [0, 200],
    [200, 0]
  ]
}
```

字段说明：

- `unit`
  - 单位
  - 必填
  - 当前固定为 `"ms"`

- `rows`
  - 行消息 ID 列表
  - 必填

- `cols`
  - 列消息 ID 列表
  - 必填

- `values`
  - 二维矩阵
  - 必填
  - 大小必须为 `rows.length x cols.length`

---

## 3.7 时序矩阵语义定义

为避免像现有 `-1/-2` 那样语义不清，建议统一改成明确的毫秒阈值规则。

### 3.7.1 推荐语义

`values[i][j]` 表示：

> 行消息 `rows[i]` 与列消息 `cols[j]` 的接收时间差最大允许值（毫秒）

也就是：

```text
abs(time(rows[i]) - time(cols[j])) <= values[i][j]
```

则视为满足联合触发条件。

### 3.7.2 对角线规则

对角线必须为：

- `0`

因为同一消息与自身的时间差恒为 0。

### 3.7.3 不参与比较的值

如果某两个消息之间不需要做时序比较，推荐使用：

- `null`

不要继续使用：

- `-1`
- `-2`

因为：

- 数值型哨兵不利于后续自动校验
- `null` 的语义更明确

### 3.7.4 示例

```json
"values": [
  [0, 200, null],
  [200, 0, 300],
  [null, 300, 0]
]
```

表示：

- `S01` 和 `S106` 时间差最大 200ms
- `S106` 和 `S201` 时间差最大 300ms
- `S01` 和 `S201` 无需比较

## 3.9 `choreography.json` 校验规则

生成器读取时应执行以下校验：

- `mode` 必须为 `joint`
- `sources.id` 唯一
- `targets.id` 唯一
- `joint_groups.group_id` 唯一
- `target_id` 必须引用有效目标
- `sources` 中所有成员都必须存在于源列表
- `rows` 和 `cols` 必须与当前组 `sources` 一致
- `values` 行列数必须匹配
- 对角线必须为 `0`
- 非空矩阵值必须为 `>= 0`
- `receive_window_ms` 必须为 `>= 0`
- `initial_status` 只能是 `direct` 或 `cache`

## 4. `mappings.json` 规范

## 4.1 设计目标

该文件只做一件事：

> 把“源协议字段 -> 公式 -> 目标协议字段”的映射规则结构化

它不描述时序、不描述收发端口、不描述协议定义本身。

---

## 4.2 顶层结构

推荐格式：

```json
{
  "version": "1.0",
  "project_name": "peach",
  "conversions": []
}
```

字段说明：

- `version`
  - 规范版本
  - 必填

- `project_name`
  - 项目名
  - 必填

- `conversions`
  - 转换链列表
  - 必填

---

## 4.3 `conversions` 结构

推荐格式：

```json
{
  "name": "S01ToW304",
  "mode": "simple",
  "sources": [
    {
      "alias": "s01",
      "protocol": "S0_1"
    }
  ],
  "target": {
    "protocol": "W304"
  },
  "rules": []
}
```

字段说明：

- `name`
  - 转换链名称
  - 必填
  - 用于生成函数名和模板名

- `mode`
  - 转换链模式
  - 必填
  - 可选值：
    - `simple`
    - `joint`

- `sources`
  - 源协议列表
  - 必填

- `target`
  - 目标协议
  - 必填

- `rules`
  - 字段规则列表
  - 必填

---

## 4.4 `sources` 定义

推荐格式：

```json
{
  "alias": "s01",
  "protocol": "S0_1"
}
```

字段说明：

- `alias`
  - 在公式表达式中使用的变量别名
  - 必填
  - 必须唯一

- `protocol`
  - 协议类型名
  - 必填
  - 必须存在于协议 XML 生成出的对象集合中

说明：

- `alias` 是表达式中唯一允许引用的根名
- 例如：
  - `s01.var15111124819`
  - `w304.var17446818739`

---

## 4.5 `target` 定义

推荐格式：

```json
{
  "protocol": "W304"
}
```

字段说明：

- `protocol`
  - 目标协议类型
  - 必填

---

## 4.6 `rules` 定义

每一条规则对应一个目标字段如何赋值。

推荐格式：

```json
{
  "target_field": "var17446773733",
  "formula": "pow(s01.var15111124819, 2)",
  "source_fields": ["s01.var15111124819"],
  "rule_type": "expression",
  "when": null,
  "default_value": null,
  "description": "目标字段由源字段平方得到"
}
```

字段说明：

- `target_field`
  - 目标协议字段名
  - 必填

- `formula`
  - 转换公式
  - 必填

- `source_fields`
  - 本规则依赖的源字段列表
  - 必填

- `rule_type`
  - 规则类型
  - 必填
  - 可选值：
    - `const`
    - `direct`
    - `expression`
    - `conditional`

- `when`
  - 生效条件
  - 可选
  - 为空表示无条件

- `default_value`
  - 当 `when` 不满足或计算失败时的回退值
  - 可选

- `description`
  - 规则说明
  - 可选

---

## 4.7 `rule_type` 语义

### 4.7.1 `const`

固定值赋值。

示例：

```json
{
  "target_field": "var1744751767",
  "formula": "2",
  "source_fields": [],
  "rule_type": "const"
}
```

### 4.7.2 `direct`

直接字段拷贝。

示例：

```json
{
  "target_field": "var16216466",
  "formula": "w304.var17446818739",
  "source_fields": ["w304.var17446818739"],
  "rule_type": "direct"
}
```

### 4.7.3 `expression`

表达式计算。

示例：

```json
{
  "target_field": "var16216466",
  "formula": "w304.var17446818739 * 0.126",
  "source_fields": ["w304.var17446818739"],
  "rule_type": "expression"
}
```

### 4.7.4 `conditional`

条件赋值。

示例：

```json
{
  "target_field": "var100",
  "formula": "s01.a > 0 ? 1 : 0",
  "source_fields": ["s01.a"],
  "rule_type": "conditional"
}
```

---

## 4.8 公式表达式语法规范

为方便安全生成 C++，建议只支持**受控表达式子集**。

### 4.8.1 允许的原子项

- 数值常量
  - `0`
  - `1`
  - `3.14`

- 布尔常量
  - `true`
  - `false`

- 字段引用
  - `s01.var15111124819`
  - `w304.var17446818739`

### 4.8.2 允许的运算符

- 算术运算
  - `+`
  - `-`
  - `*`
  - `/`
  - `%`

- 比较运算
  - `==`
  - `!=`
  - `>`
  - `>=`
  - `<`
  - `<=`

- 逻辑运算
  - `&&`
  - `||`
  - `!`

- 条件运算
  - `?:`

### 4.8.3 允许的内置函数

建议白名单如下：

- `abs(x)`
- `min(a, b)`
- `max(a, b)`
- `pow(a, b)`
- `round(x)`
- `floor(x)`
- `ceil(x)`
- `clamp(x, low, high)`

### 4.8.4 可选扩展函数

如果后续业务需要，可以再扩展：

- `deg2rad(x)`
- `rad2deg(x)`
- `scale(x, factor)`
- `ifnull(x, fallback)`

---

## 4.9 公式表达式禁止项

为了保证生成结果安全、稳定，必须禁止：

- 任意 C++ 代码块
- `;`
- `#include`
- `return`
- `for`
- `while`
- `if (...) { ... }`
- lambda
- 指针访问
- 任意对象构造
- 文件 IO
- 网络调用
- 系统命令

也就是说：

> `formula` 只能是一个纯表达式，不能是语句块。

---

## 4.10 `when` 规范

`when` 用于表达“只有在某个条件满足时，这条规则才生效”。

推荐格式：

```json
"when": "s01.valid_flag == 1"
```

语义：

- 如果条件成立，则执行 `formula`
- 如果条件不成立：
  - 有 `default_value` 时使用默认值
  - 否则保持目标字段默认初始化值

## 4.12 `mappings.json` 校验规则

生成器应执行以下校验：

- `version` 必填
- `project_name` 必填
- `conversions.name` 唯一
- `sources.alias` 在当前转换内唯一
- `target.protocol` 必须存在
- `target_field` 必须存在于目标协议定义
- `source_fields` 中每个字段都必须存在
- `formula` 中引用的字段必须全部出现在 `source_fields` 或内置常量中
- 同一个转换内，`target_field` 不允许重复赋值
- `rule_type=const` 时 `source_fields` 应为空
- `rule_type=direct` 时建议 `source_fields.length == 1`
- `when` 和 `formula` 都必须是合法表达式
- 禁止出现未授权关键字与非法字符

## 5. 生成器读取后的中间模型建议

为了和上层设计文档对齐，建议读取后转为以下两个 IR。

### 5.1 `ChoreographyIR`

```json
{
  "enabled": true,
  "project_name": "peach",
  "sources": [],
  "targets": [],
  "joint_groups": []
}
```

### 5.2 `MappingIR`

```json
{
  "project_name": "peach",
  "conversions": []
}
```

然后由模板层分别渲染：

- `ChoreographyIR -> to_code_Choreography.cpp`
- `MappingIR -> xxx_to_yyy.cpp`

## 6. 推荐的文件命名

建议固定命名，便于生成器实现：

- `protocols/`
  - 存放协议 XML

- `mappings.json`
  - 存放转换公式

- `choreography.json`
  - 仅联合转换时提供

示例：

```text
input/
├── protocols/
│   ├── s0_1.xml
│   ├── s106.xml
│   ├── w204.xml
│   └── w304.xml
├── mappings.json
└── choreography.json
```

## 7. 最终推荐结论

### 7.1 时序矩阵输入规范

建议设计为：

- 顶层包含 `sources`、`targets`、`joint_groups`
- 每个联合组显式给出 `matrix`
- 矩阵值统一使用**毫秒阈值**
- 不参与比较时使用 `null`
- 不再使用 `-1/-2` 这种隐式哨兵值

### 7.2 转换公式输入规范

建议设计为：

- 每条转换链一个 `conversion`
- 每个目标字段一个 `rule`
- `rule` 至少包含：
  - `target_field`
  - `formula`
  - `source_fields`
  - `rule_type`
- 表达式必须是受控子集
- 禁止任意 C++ 语句注入

### 7.3 与模板生成的关系

- `protocol xml` 生成：`*_def.h`、`codec.*`
- `mappings.json` 生成：`xxx_to_yyy.*`
- `choreography.json` 生成：`to_code_Choreography.*`
- 运行时壳模板生成：`main.cpp`、`messageconvert.*`、`config.xml`、`peach.pro`

---

## 8. 一句话总结

> `mappings.json` 解决“怎么转”，`choreography.json` 解决“什么时候能转、几条链怎么协同转”。
