# 协议转换项目生成器设计方案

本文档用于回答一个具体目标：

> 如何从现有 `newB`、`newC`、`newD` 三个项目中提炼公共部分，抽象成统一模板；然后仅通过输入：
>
> - 协议 `xml`
> - 联合转换场景下的时序关系矩阵
> - 转换公式 `json`（包含原协议字段、转换公式、目标协议字段）
>
> 自动生成类似的 Qt/C++ 协议转换项目。

---

## 1. 设计目标

本生成器的目标不是只生成某一个项目，而是生成**一类同构的协议转换项目**。

这类项目的共同特点是：

- 基于 Qt/C++
- 通过 `config.xml` 配置收发端口
- 通过 `main.cpp` 启动
- 通过 `messageconvert.*` 完成运行时收包、缓存、调度、转换、发包
- 通过 `*_def.h + codec.*` 实现协议数据结构与编解码
- 通过 `xxx_to_yyy.*` 实现字段映射
- 在多消息联合转换场景下，通过 `to_code_Choreography.*` 实现时序编排

因此，生成器要解决的是：

1. **公共代码模板化**
2. **协议定义代码自动生成**
3. **字段映射代码自动生成**
4. **联合转换编排代码按需生成**

---

## 2. 三个现有项目的公共部分

### 2.1 完全公共的骨架

三个项目都具备以下公共文件：

- `main.cpp`
- `messageconvert.h`
- `messageconvert.cpp`
- `codec.h`
- `codec.cpp`
- `config.xml`
- `peach.pro`
- `peach.pro.user`

这说明它们的**运行时壳子**和**工程组织方式**是统一的。

### 2.2 可参数化的公共部分

以下部分虽然文件不同，但本质上是同一类东西：

- `*_def.h`
  - 协议对象定义
- `xxx_to_yyy.h/.cpp`
  - 转换函数定义与实现
- `codec.cpp`
  - 针对具体协议生成的编解码逻辑

这些内容不需要手写模板正文，而应该由输入数据生成。

### 2.3 可选公共部分

只有 `newB` 里有：

- `to_code_Choreography.h`
- `to_code_Choreography.cpp`

这说明：

- **单消息单链路转换**不需要编排文件
- **多消息联合转换/多链路协同转换**才需要编排文件和时序矩阵

这与需求完全一致，因此可以设计成：

- 简单转换模板：不生成编排文件
- 联合转换模板：生成编排文件

## 3. 三个项目的差异点

生成器真正要参数化的差异，主要只有 4 类。

### 3.1 协议集合不同

- `newB`：`S0_1`、`S106`、`W304`、`W204`
- `newC/newD`：`W304`、`ICD304`

### 3.2 转换链不同

- `newB`
  - `S0_1 -> W304`
  - `S106 -> W204`

- `newC/newD`
  - `W304 -> ICD304`

### 3.3 运行模式不同

- `newB`：多链路、带缓存有效期、带时序判定、支持目标消息暂存
- `newC/newD`：单链路、直接转换、没有额外编排层

### 3.4 映射公式不同

例如：

- 常量赋值
- 直接字段拷贝
- 简单算术表达式
- 数学函数表达式

这些差异应由转换公式 `json` 驱动，而不是手工写在 `.cpp` 里。

## 4. 统一模板的总体架构

建议将生成器拆成 5 个子模块。

### 4.1 `xml_parser`

负责：

- 读取协议 XML
- 解析消息结构
- 构建统一中间模型

输出：

- `ProtocolIR`

### 4.2 `formula_parser`

负责：

- 读取转换公式 JSON
- 校验源字段、目标字段、表达式
- 构建转换规则中间模型

输出：

- `MappingIR`

### 4.3 `matrix_parser`

负责：

- 读取联合转换场景的时序关系矩阵
- 解析有效时间窗、源消息间约束、目标状态初始化等内容

输出：

- `ChoreographyIR`

### 4.4 `project_planner`

负责：

- 根据输入判断生成哪种模板
- 规划需要生成哪些文件

输出：

- `ProjectPlan`

### 4.5 `code_renderer`

负责：

- 将中间模型套入模板
- 输出完整项目目录

输出：

- C++ 项目文件集合

## 5. 推荐的中间模型设计

为了让模板清晰，建议不要直接拿 XML/JSON 生成代码，而是先统一为中间模型。

### 5.1 协议中间模型 `ProtocolIR`

```json
{
  "protocol_name": "W304",
  "namespace": "w/w304",
  "endian": "big",
  "word_length": -1,
  "messages": [
    {
      "name": "W304",
      "segments": [
        {
          "type": "origin",
          "fields": [
            {"name": "field_a", "bit_length": 8, "data_type": "int", "default": 0}
          ]
        }
      ],
      "sequences": [
        {"name": "Seq_1", "cycle": 0, "times": 1}
      ]
    }
  ]
}
```

### 5.2 转换中间模型 `MappingIR`

```json
{
  "conversion_name": "S01ToW304",
  "sources": ["S0_1"],
  "target": "W304",
  "rules": [
    {
      "target_field": "var17446773733",
      "source_fields": ["S0_1.var15111124819"],
      "expression": "pow(S0_1.var15111124819, 2)"
    },
    {
      "target_field": "var1744751767",
      "source_fields": [],
      "expression": "2"
    }
  ]
}
```

### 5.3 编排中间模型 `ChoreographyIR`

```json
{
  "enabled": true,
  "dest_protocols": ["W协议.W30_4", "W协议.W20_4"],
  "template_names": ["S01ToW304", "S106ToW204"],
  "status_list": [false, false],
  "src_protocols": ["S协议.S0_1", "S协议.S106"],
  "receive_windows": [200, 200],
  "source_time_matrix": [
    [-1, -2],
    [-2, -1]
  ]
}
```

### 5.4 项目规划模型 `ProjectPlan`

```json
{
  "project_name": "peach",
  "project_mode": "simple | joint",
  "sources": ["S0_1", "S106"],
  "targets": ["W304", "W204"],
  "generate_choreography": true,
  "files": ["main.cpp", "messageconvert.cpp", "codec.cpp"]
}
```

## 6. 输入模型设计

最终建议生成器接收 3 类输入。

### 6.1 输入一：协议 XML

作用：

- 定义每个协议的数据结构
- 生成 `*_def.h`
- 生成 `codec.h/.cpp`

推荐组织形式：

```text
protocols/
  s0_1.xml
  s106.xml
  w204.xml
  w304.xml
```

如果是带总索引的协议族，也可以：

```text
protocols/
  k.xml
  k1.6.xml
  k1.7.xml
  k5.1.xml
```

### 6.2 输入二：时序关系矩阵

作用：

- 仅用于**联合转换**
- 决定多源消息是否满足联合触发条件
- 决定目标消息缓存有效期
- 决定是否需要暂存/等待其他消息

使用规则：

- **单源单目标转换：不需要**
- **多源联合转换：必须提供**

推荐格式：

```json
{
  "enabled": true,
  "dest_protocols": ["W协议.W30_4", "W协议.W20_4"],
  "template_names": ["S01ToW304", "S106ToW204"],
  "status_list": [false, false],
  "src_protocols": ["S协议.S0_1", "S协议.S106"],
  "receive_windows": [200, 200],
  "source_time_matrix": [
    [-1, -2],
    [-2, -1]
  ]
}
```

### 6.3 输入三：转换公式 JSON

这是最核心的输入。

作用：

- 定义源协议字段如何计算到目标协议字段
- 替代手写 `xxx_to_yyy.cpp`

推荐格式：

```json
{
  "project_name": "peach",
  "conversions": [
    {
      "conversion_name": "S01ToW304",
      "sources": ["S0_1"],
      "target": "W304",
      "rules": [
        {
          "target_field": "var1744751767",
          "source_fields": [],
          "expression": "2"
        },
        {
          "target_field": "var17446773733",
          "source_fields": ["S0_1.var15111124819"],
          "expression": "pow(S0_1.var15111124819, 2)"
        }
      ]
    },
    {
      "conversion_name": "W304ToICD304",
      "sources": ["W304"],
      "target": "ICD304",
      "rules": [
        {
          "target_field": "var16216466",
          "source_fields": ["W304.var17446818739"],
          "expression": "W304.var17446818739 * 0.126"
        }
      ]
    }
  ]
}
```

## 7. 模板分层设计

建议将模板分为 4 层。

### 7.1 工程壳模板

固定模板文件：

- `main.cpp.tpl`
- `peach.pro.tpl`
- `config.xml.tpl`

作用：

- 提供 Qt 项目外壳
- 注入协议文件名、转换类名、工程源文件列表

### 7.2 运行时模板

分两种：

#### A. 简单转换模板

适用于：

- 单源单目标
- 不需要联合触发
- 不需要时序矩阵

生成文件：

- `messageconvert.h`
- `messageconvert.cpp`

特点：

- 单一 `XXXdataPro()`
- 无 `to_code_Choreography.*`
- 无额外定时器缓存清理逻辑

对应现有项目：

- `newC`
- `newD`

#### B. 联合转换模板

适用于：

- 多种消息并存
- 多转换链并存
- 需要联合触发或时序控制

生成文件：

- `messageconvert.h`
- `messageconvert.cpp`
- `to_code_Choreography.h`
- `to_code_Choreography.cpp`

特点：

- 多个 `XXXdataPro()`
- 有缓存有效期检查
- 有消息时序判定
- 有状态位与暂存逻辑

对应现有项目：

- `newB`

### 7.3 协议代码模板

生成文件：

- `*_def.h`
- `codec.h`
- `codec.cpp`

作用：

- 由 XML 自动生成协议类和编解码器

### 7.4 映射代码模板

生成文件：

- `xxx_to_yyy.h`
- `xxx_to_yyy.cpp`

作用：

- 由公式 JSON 自动生成转换函数

## 8. 生成策略：如何判断该选哪个模板

生成器应先做一次项目模式判定。

### 8.1 判定规则

如果满足以下任一条件，则选择 **joint 模板**：

- 转换链数量 > 1
- 某个目标消息依赖多个源消息联合触发
- 提供了时序关系矩阵
- 明确要求目标消息缓存和时序约束

否则选择 **simple 模板**。

### 8.2 模板选择结果

#### `simple`

生成：

- `main.cpp`
- `messageconvert.h`
- `messageconvert.cpp`
- `codec.h`
- `codec.cpp`
- `config.xml`
- `peach.pro`
- `*_def.h`
- `xxx_to_yyy.h/.cpp`

不生成：

- `to_code_Choreography.*`

#### `joint`

生成：

- 上述所有文件
- 额外生成 `to_code_Choreography.h/.cpp`

## 9. 代码生成流程

建议完整流程如下。

### 第 1 步：读取输入

- 读取协议 XML
- 读取转换公式 JSON
- 如有联合转换，则读取时序矩阵 JSON

### 第 2 步：构建中间模型

- `ProtocolIR`
- `MappingIR`
- `ChoreographyIR`
- `ProjectPlan`

### 第 3 步：生成协议层代码

输出：

- `*_def.h`
- `codec.h`
- `codec.cpp`

### 第 4 步：生成映射层代码

输出：

- `xxx_to_yyy.h`
- `xxx_to_yyy.cpp`

### 第 5 步：生成运行时层代码

根据模板模式输出：

- `messageconvert.h`
- `messageconvert.cpp`
- 可选 `to_code_Choreography.h/.cpp`

### 第 6 步：生成工程文件

输出：

- `main.cpp`
- `config.xml`
- `peach.pro`

### 第 7 步：输出项目目录

最终得到一个完整可编译的 Qt/C++ 项目。

## 11. `messageconvert` 模板如何抽象

这是生成器中最值得模板化的部分。

### 11.1 公共部分

以下逻辑对三个项目都是通用的：

- 创建发送 socket
- 创建接收 socket
- 绑定 `readyRead`
- 收包后封装为 `msgDataInfo`
- 缓存数据
- 转换线程循环
- 编码后调用统一发送函数

这些应放入基础模板。

### 11.2 变化部分

变化的是：

- 处理函数数量
- 每个处理函数对应的源协议名
- 每个处理函数调用哪个映射函数
- 是否需要额外的时序检查
- 是否需要目标消息缓存清理

因此推荐做成：

- `messageconvert.base.tpl`
- `messageconvert.simple.tpl`
- `messageconvert.joint.tpl`

其中：

- `base.tpl` 负责通用成员和公用函数
- `simple.tpl` 负责单链路处理函数展开
- `joint.tpl` 负责多链路和编排逻辑展开

## 12. `codec` 模板如何抽象

`codec.cpp` 很大，但结构是高度重复的。

可按下面方式生成：

### 12.1 通用固定模板

保留通用位操作函数模板：

- `readBits`
- `readBitsLE`
- `appendBits`
- `readBits_d`
- `appendBits_d`

### 12.2 协议展开模板

针对每个协议 IR，自动展开：

- `readOrigin`
- `readProlong`
- `readContinueN`
- `read{Proto}`
- `writeOrigin`
- `writeContinueN`
- `writeSeq_N`
- `checkConstraint_X`
- `VerifyField`
- `updateFieldValue`
- `updateGroupFlag`
- `decodeMsg`
- `encodeMsg`
- `checkObjMaps`

也就是说，`codec.cpp` 应被设计为：

- 一部分固定模板
- 一部分协议片段循环展开

## 13. 转换公式 JSON 的约束建议

为了保证可生成性，建议表达式只允许受控子集。

### 13.1 建议支持的表达式类型

- 常量：`2`
- 直接拷贝：`S0_1.a`
- 四则运算：`S0_1.a + 3`
- 数学函数：`pow(S0_1.a, 2)`
- 条件表达式：`S0_1.a > 0 ? 1 : 0`

### 13.2 建议禁止的内容

- 任意 C++ 语句块
- 自定义循环
- 任意系统调用
- 任意 include 注入

### 13.3 推荐做法

不要把 JSON 中的表达式原样拼进 C++，而是：

1. 先解析为表达式 AST
2. 再将 AST 渲染为安全的 C++ 子表达式

这样可以避免生成恶意代码或格式错误代码。

## 14. 关于“联合转换才需要时序矩阵”的最终设计结论

这个规则建议直接固化在生成器中。

### 14.1 simple 模式

输入：

- 协议 XML
- 转换公式 JSON

不需要：

- 时序矩阵

生成结果：

- 类似 `newC/newD`

### 14.2 joint 模式

输入：

- 协议 XML
- 转换公式 JSON
- 时序矩阵 JSON

生成结果：

- 类似 `newB`

这样能保证：

- 简单项目配置不被复杂化
- 多消息协同项目保留完整能力

## 16. 最终推荐方案

综合三个现有项目的共同点与差异，推荐最终方案如下：

### 16.1 采用“单模板体系 + 双模式输出”

即一个生成器，内部支持：

- `simple` 模式
- `joint` 模式

而不是分开做多个独立生成器。

### 16.2 输入统一为三类

- 协议 XML
- 转换公式 JSON
- 可选时序矩阵 JSON

### 16.3 输出统一为 Qt/C++ 工程

输出项目结构与现有项目一致，方便：

- 与现有代码合并
- 按原有方式编译
- 继续人工维护

### 16.4 模板与生成边界明确

#### 适合模板化的

- 工程骨架
- 运行时壳子
- 编排文件
- 协议编解码结构

#### 适合数据驱动生成的

- 协议字段
- 约束逻辑
- 转换公式
- 时序关系矩阵

---

## 17. 一句话总结

这三个项目的本质可以抽象成一个统一公式：

> **Qt 工程壳 + 协议 XML 生成的编解码器 + 公式 JSON 生成的映射函数 + （联合转换时）时序矩阵生成的编排文件**

只要把这四部分拆清楚，就可以稳定生成与 `newB/newC/newD` 同类的 C++ 协议转换项目。
